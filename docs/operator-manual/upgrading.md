# Upgrading

## Helm

See [Helm installation](./installation/helm.md#upgrading) for more information.

## From v0.4.0 or earlier

Release charts are now pinned by digest (see [Rendering Pipeline](../developer-guide/rendering-pipeline.md#stage-1-release-rendertasks)). This has two effects during the upgrade:

- **Every Release is rendered again.** The release chart tag now includes a hash of the component reference and the resource references (repository, tag, insecure flag), so the tag changes for every Release, pinned or not. Each release chart and each Target's bootstrap chart is rendered and pushed once more, and Flux upgrades the corresponding HelmReleases. For a ComponentVersion that did not change, the rendered content is the same apart from the chart tag, so the workloads themselves are not upgraded. Expect a burst of render Jobs and registry pushes right after the controller restarts.
- **Releases whose descriptor tag was re-pushed stop rendering.** If a component descriptor's tag was overwritten after discovery, the render of a ComponentVersion with a recorded `spec.digest` now fails with "the tag was overwritten after discovery" instead of quietly using the new content. The Target keeps its previously deployed bootstrap until all of its release renders succeed, so this also holds back updates to the Target's other Releases; its `ReleasesRendered` condition is `False` with reason `ReleaseFailed`. A failed RenderTask is not retried, so after restoring the original tag, delete the failed RenderTask to have it recreated. Alternatively, publish the new content as a new component version and point the Release at it. Deleting the ComponentVersion does not help: while a Release references it, its deletion stays blocked. ComponentVersions discovered before v0.4.0 have no `spec.digest`, so their descriptor is not checked.

Only newly discovered ComponentVersions get pinned resources. Existing ones keep their tag-based resource references, because the registry scan skips ComponentVersions that already exist. They get pinned only if a registry webhook reports the descriptor again. With a recorded `spec.digest`, the report must carry that digest. Without one, the ComponentVersion takes whatever descriptor the tag points to at that time, so check that it is the expected one. To pin a deployed component by hand, publish it as a new component version and point its Releases at it. Only resources with an `ociArtifactDigest/v1` digest in the descriptor are pinned; check `spec.resources` for `@sha256:` tags.

The solar-agent now reports more reliably (see [Setting up the solar-agent](./solar-agent.md#agent-liveness)). This changes six things during the upgrade:

- **The agent reads only its Target's Flux objects.** An agent delivered through SolAr now watches the bootstrap namespace only, and the agent chart's own default (`watchNamespace` empty) is its release namespace. Before, both watched all namespaces, which also reported other Targets' releases on a shared cluster. To keep the old behaviour, set `watchNamespace: "*"` in the agent Release's `values`.
- **Old agent credentials are cleaned up.** With Flux's default settings, helm-controller appends the chart digest to the version the agent reports, so superseded `solar-agent-<target>-<n>` Secrets were never deleted. Right after the upgrade, the controller deletes them for every Target whose agent already runs the current credential.
- **UI users need read access to `targetreports`.** The Target page's Agent card reads the report with the user's own credentials. Grant `get`, `list` and `watch` on `targetreports` wherever users can read Targets, as the [example roles](../developer-guide/roles.md) do. Without it, the card shows the agent's state without the time of the last report, and the UI server logs a watch error for each open browser session.
- **The Target page lists cross-namespace bindings.** Bound releases now come from the Target's new `status.resolvedBindings`, which also names bindings from other namespaces, each read with the user's own credentials. A binding the user may not read shows as its namespace and name with `No access to details`. Until the controller has reconciled a Target after the upgrade, the page lists the Target namespace's bindings as before. `ReleaseBinding` now has a `/status` subresource, so its status can no longer be changed through an update of the whole object.
- **Bindings show their deployment state.** On Targets with an agent, each `ReleaseBinding` gets a `Deployed` condition from the agent's report, and the Target page shows it on the release's row instead of the render phase (see [Reading a release's deployment state](./solar-agent.md#reading-a-releases-deployment-state)). A render failure still shows first, now labelled `Render failed`.
- **Target health includes deployment.** The Target's new `ReleasesDeployed` condition rolls up its bindings, and the health badge now also shows `Failed` and `Progressing`, and `Degraded` for a failed preflight check (see [A Target's overall state](./solar-agent.md#a-targets-overall-state)). A release is only `Ready` once its live chart digest matches the rendered chart's, which the controller reads from the render registry. Right after the upgrade it reads the digest of every bound `RenderArtifact` once, and releases stay `Progressing` until their digest is known. Targets without an agent are judged by rendering alone, as before.
